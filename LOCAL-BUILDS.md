# Local Android builds

Everything needed to build the Android APK on this PC, with no EAS build and no
monthly build quota. iOS still has to be built through EAS — it needs macOS.

## What is installed

| Tool | Version | Location |
|---|---|---|
| JDK | 21.0.12 LTS | `C:\Program Files\Microsoft\jdk-21.0.12.101-hotspot` |
| Android cmdline-tools | 19.0 | `%LOCALAPPDATA%\Android\Sdk\cmdline-tools\latest` |
| Platform | android-35 | |
| Build-tools | 35.0.0 | |
| NDK | 27.1.12297006 | needed because the New Architecture compiles C++ |
| CMake | 3.22.1 | needed for the same reason |
| Gradle | 9.3.1 | downloaded automatically by the wrapper |

`JAVA_HOME`, `ANDROID_HOME` and `ANDROID_SDK_ROOT` are set at the user level, and
the `bin` directories were added to the user `PATH`. **Open a new terminal** before
relying on that, since existing shells keep the old environment.

## Building

```powershell
cd D:\work-tracker

.\build-apk.ps1                            # debug APK
.\build-apk.ps1 -Variant release           # standalone APK, JS bundled in
.\build-apk.ps1 -Variant release -Install  # build, then install over USB
```

Output lands in `android\app\build\outputs\apk\<variant>\`.

The script builds only `arm64-v8a` by default, which is what the A34 uses. Building
all four ABIs is roughly four times slower for no benefit here. Pass `-Abi` to
change it.

### Debug versus release

- **Debug** loads JavaScript from the Metro dev server at runtime, so the phone has
  to reach this PC. Fast to iterate with, but it will not start without Metro.
- **Release** embeds the JS bundle, so it runs entirely on its own. This is the one
  to install if you want to test the app the way a real user would.

Release builds are signed with the auto-generated **debug** keystore, which is
Expo's default and is fine for sideloading onto your own phone. It is not
acceptable for the Play Store, which needs a real upload key.

## A caveat about prebuild

`android\gradle.properties` is generated by `npx expo prebuild`, and the Gradle
memory settings were raised there from Expo's 2g/512m default — the daemon was
exhausting Metaspace and dying at the end of every build, which made each
subsequent build cold again. **`npx expo prebuild --clean` will overwrite that
line.** Re-apply it if you ever do a clean prebuild.

## Installing on the phone

Over USB is the reliable route, because this PC is on Ethernet and the phone is on
Wi-Fi — `adb reverse` tunnels through the cable so the phone can reach Metro at
`localhost:8081` regardless of the network.

1. On the phone: Settings → About phone → tap **Build number** seven times.
2. Settings → Developer options → **USB debugging** on.
3. Plug in the phone and accept the "Allow USB debugging?" prompt.
4. `.\build-apk.ps1 -Variant release -Install`

Verify with `adb devices`; the device must show as `device`, not `unauthorized`.

## EAS Update

`expo-updates` is installed and configured, so **JavaScript-only changes can be
pushed to an already-installed app with no rebuild**:

```powershell
cd D:\work-tracker
$env:EAS_NO_VCS="1"
eas update --channel preview --message "what changed"
```

The app picks the update up on next launch. This sidesteps the 15-builds-per-month
cap entirely, since only the first build after this change was a real build.

Two things it cannot do, because they are native:

- changing anything in `app.json`'s `android`/`ios` blocks, the `plugins` list, or
  native dependencies
- anything requiring a new native module

Those still need a rebuild — locally, which is now free.

`runtimeVersion` uses the `appVersion` policy, so the app version in `app.json` has
to change before an update will apply across a release. During development the
`preview` channel is fine as-is.
